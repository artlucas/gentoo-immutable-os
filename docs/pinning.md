# Pinning

A rebuild of a release selects the same versions because every build input is pinned. Pins live in `config/build.conf`; locks live in `config/portage/lock/` and `config/flatpak/apps.lock`. Pins say which inputs; locks record and constrain the resolution.

## Pin matrix

| Pin | Location | Pins | Enforcement |
|---|---|---|---|
| `BUILDER_IMAGE` + `BUILDER_DIGEST` | `config/build.conf` | The stage3 base image, by digest | The builder image builds `FROM gentoo/stage3:amd64-systemd@sha256:…`. An empty digest is a hard failure unless `ALLOW_UNPINNED=1`; such builds write `out/state/unpinned-build` and stage 80 refuses to release them |
| `SNAPSHOT_DATE` + `SNAPSHOT_SHA256` | `config/build.conf` | The ebuild tree: the exact bytes of `gentoo-<date>.tar.xz` | Stage 10 verifies upstream's digest and GPG signature, then checks the tarball against `SNAPSHOT_SHA256`; the `.tree-pin` marker in the tree volume carries the pin and every depgraph stage asserts it |
| `PROFILE` | `config/build.conf` | The Gentoo portage profile | Recorded in every image lock header |
| `<profile>.lock` | `config/portage/lock/` | Every target package at an exact atom | Stage 20 renders the lock into the `@locked-image` set; stage 30 emerges `@locked-image` and nothing else, then verifies the installed database against the lock in both directions |
| `builder.lock` | `config/portage/lock/` | The builder's own closure | Stage 10 asserts the builder's installed packages against it |
| `apps.lock` | `config/flatpak/` | Every preinstalled Flatpak ref — apps and runtimes — to an exact Flathub commit | Stage 40 deploys each pinned commit and asserts the readback |
| `VERSION` | `config/build.conf` | Release identity | Must strictly increase across releases (strverscmp order); the GPT root partlabel `root_<VERSION>` derives from it |

!!! warning "Snapshot retention"
    distfiles.gentoo.org keeps roughly nine days of dated snapshots. After that window, a moved pin can only be restored from a stage-90 vendored archive. Capture a new pin while it is live, and vendor every release.

## Lock file format

A lock is a commented provenance header followed by one exact atom per line, sorted and unique under `LC_ALL=C`:

```text
# desktop.lock — the pre-prune --root=$TARGET closure, exactly as stage 30 resolves it
#
# SNAPSHOT_SHA256: c61294000825031e58a38f60fadb603423c61430b841d73b87705f789d83944b
# SNAPSHOT_DATE: 20260820
# PROFILE: default/linux/amd64/23.0/desktop/plasma/systemd
# PORTAGE_CONFIG_HASH: 1f0e3dad999d...
# INCLUDE_CJK_FONTS: 1
# INCLUDE_PRINTING: 1
# INCLUDE_DISTROBOX: 1
# PROFILE_ROLE: target
# BUILD_PROFILE: desktop
# PROFILE_SETS: base hardware domain desktop
#
=acct-group/audio-0-r3
=app-arch/zstd-1.5.7
...
```

Locks are generated by `scripts/relock.sh` and committed. Never hand-edit the atom list; see [Relock](relock.md).

Header keys of an image lock:

| Key | Meaning |
|---|---|
| `SNAPSHOT_SHA256`, `SNAPSHOT_DATE` | The tree the lock was resolved against |
| `PROFILE` | The portage profile in effect |
| `PORTAGE_CONFIG_HASH` | `portage_config_hash()` at generation time — the fingerprint of the config the atoms answer to |
| `INCLUDE_CJK_FONTS`, `INCLUDE_PRINTING`, `INCLUDE_DISTROBOX` | Build switches that change the closure through set markers (`#cjk`, `#printing`, `#distrobox`) |
| `PROFILE_ROLE` | `target` or `live`; recorded for provenance only — since [plan/34 §6](../plan/34-installer-sysext.md) it no longer changes set membership. There is no `#not-live` marker any more: a `live` profile's tree must be the matching `target` profile's tree plus its own tail, at identical versions, because the tail ships as a `systemd-sysext` difference that cannot represent a deletion |
| `BUILD_PROFILE`, `PROFILE_SETS` | Which profile file and which set names produced the closure |

`builder.lock` records only the two `SNAPSHOT_*` keys. The builder resolves against an `/etc/portage` that `builder/Dockerfile` writes inline and reads nothing from `config/portage`, so the other keys do not describe it. The omission also protects the build cache: the Dockerfile copies `builder.lock`, and Docker keys that layer — and roughly an hour of source builds behind it — on the file's content. A `PORTAGE_CONFIG_HASH` line in the file would rebuild the builder for every comment edit under `config/portage`.

## The config fingerprint

`portage_config_hash()` computes a SHA-256 over every file under `config/portage` (excluding `expected-packages*` and `lock/`) plus `config/build.conf`, using relative paths and `LC_ALL=C` sorting so the value is checkout-location-independent. Every image lock header records it, and stage 20 asserts it one-way: the lock's recorded hash must match the current config.

Consequence: any edit under `config/portage` or to `config/build.conf` that changes the hash stops every build until the locks carry the new hash — through a [re-resolve](relock.md) when versions should move, or through `--restamp` when they should not. This is the mechanism that makes "the config changed but the lock did not" a build failure instead of a silent drift.

## Requests versus locks

Maintainers edit the request side; the build consumes the lock side:

- Requests: `config/portage/sets/*` (loose package names with `#cjk`/`#printing`/`#distrobox` markers), `config/portage/package.use/`, `package.mask/`, `package.accept_keywords/`, `package.license/`, and the ebuilds under `config/portage/overlay/`.
- Locks: `config/portage/lock/<profile>.lock` — the resolution of those requests against the pinned tree.

!!! important "Invariant"
    Stage 30 emerges `@locked-image` and nothing else. A package the lock does not name is never built, whatever the sets request. Adding an entry to a set or an ebuild to the overlay has no effect until a re-resolve records it in the lock.

## Flatpak pin

`config/flatpak/apps.lock` holds one `<ref> <flathub-commit>` pair per line, apps and runtimes both. It is the least durable pin in the build: Flathub garbage-collects old commits faster than Gentoo drops ebuild versions. Regenerate it with `scripts/relock.sh --flatpak` after a build; vendor every release to keep the pinned commits fetchable.

## Escape hatch

`ALLOW_UNPINNED=1` permits a build against the floating `BUILDER_IMAGE` tag when `BUILDER_DIGEST` is empty. The run writes the `out/state/unpinned-build` marker, and stage 80 refuses to assemble a release from it. Use it for throwaway development builds only.
