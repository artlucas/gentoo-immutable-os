# 18 — Active Directory domain join

An immutable, Flatpak-first desktop is a good fit for a managed fleet, and a managed fleet in
practice means Windows Active Directory. This document specifies joining one: what the image
ships so that it is *domain-ready*, what a join writes, how the installer offers it, and what
each of those costs.

Two properties shape every decision below, and both come from [plan/01](01-architecture.md):

1. **`/etc` is an overlay with no 3-way merge.** A file the OS ships and the user modifies stops
   receiving vendor updates forever. So the image ships every file the AD stack needs *already
   configured*, and a join writes only files that did not exist before. Joining is data, not
   reconfiguration.
2. **A failed unit is a failed boot.** `systemd-boot-check-no-failures.service` gates
   `boot-complete.target`, which is what marks a UKI good. An authentication daemon that fails to
   start on an unjoined machine does not produce a warning — it produces an automatic rollback to
   the previous image. §5 is about that.

## 1. The decision

**`sys-auth/sssd` with the `ad` provider, joined by `app-crypt/adcli`.** No realmd, and winbind is
built but never run — see §5.4, which is the correction to an earlier version of this line that
claimed it was not built at all. The installer uses Calamares' **stock** users page and a `realm`
shim; there is no custom C++ view module.

| Candidate | Verdict |
|---|---|
| **sssd + adcli** | **Chosen.** Both stable `amd64` in the pinned tree. The industry-standard Linux AD client: offline credential caching, SID-derived id mapping with no schema changes, DC failover and site discovery, KEYRING ccaches. `adcli` is a single small C program whose only deps (`mit-krb5`, `openldap[sasl]`) sssd already pulls |
| realmd | **Not in the Gentoo tree at all.** It is also only a d-bus wrapper around adcli + sssd config generation — which is what §4's CLI is. Its absence costs a dependency, not a capability |
| Samba winbind | Fewer new atoms on `desktop` (samba is already there for `smb://`), but weaker offline logon, id-mapping that shifts if `idmap config` is ever wrong, and no KCM. It would also mean `net-fs/samba[ads,winbind,python]` — a USE change on a package every profile shares. NB: choosing sssd did **not** avoid the winbind flag. `sys-auth/sssd[samba]` is mandatory for the AD provider (§5.4) and its dependency is `net-fs/samba[winbind]`, so the image builds winbind either way — it just never runs it |
| `nss-pam-ldapd` / raw LDAP + krb5 | Works, and is what sssd replaced everywhere for good reason: no caching, no offline login, no id mapping, no failover |

## 2. What the image ships

All of this is in the read-only EROFS lower, on **every** profile, and none of it is touched by a
join. The `@domain` set names two atoms; everything else resolves.

| Shipped | Why it must be shipped rather than written at join time |
|---|---|
| `sys-auth/sssd`, `app-crypt/adcli` + closure | There is no Portage on the target. Nothing can be installed later, by design |
| `/etc/nsswitch.conf` naming `sss` | Editing it at join time would copy it up and freeze it against every future release |
| PAM stacks carrying `pam_sss.so`, from `sys-auth/pambase[sssd]` | Same reason, and worse: a hand-edited `/etc/pam.d/system-auth` frozen at one release's content is how a future PAM change locks a machine out |
| `/etc/krb5.conf` with `includedir /etc/krb5.conf.d/` | So a join writes a *new* file into the include dir instead of rewriting the vendor one |
| `sssd.service`, disabled, with a `ConditionPathExists` drop-in | §5 |
| `/usr/bin/<id>-domain` | The join implementation itself (§4) |

**Unjoined behaviour is the load-bearing property.** With no sssd socket, `nss_sss` returns
unavailable and the next NSS module answers; `pam_sss` returns `PAM_AUTHINFO_UNAVAIL` or
`PAM_USER_UNKNOWN` and the stack falls through to `pam_unix`. An image that ships all of the above
and is never joined must be indistinguishable from today's, and that is asserted rather than
assumed — see T-DOM-4 in §7.

### 2.1 nsswitch

```
passwd:     files sss systemd
group:      files [SUCCESS=merge] sss [SUCCESS=merge] systemd
shadow:     files systemd
```

`shadow` deliberately does **not** gain `sss`: sssd's NSS responder does not serve shadow entries,
and authentication goes through `pam_sss`, not through a shadow lookup. `hosts` is unchanged —
`resolve [!UNAVAIL=return] files myhostname dns`, for the reasons that file already documents.

Stage 40's NSS verification loop, which asserts a real `libnss_<m>.so` exists for every module
named, gains `sss` along with the file.

### 2.2 PAM

`sys-auth/pambase[sssd]`. The stack is **generated by the ebuild**, not written here — which keeps
the repo's existing property that `config/rootfs/` contains no `/etc/pam.d` at all, and means a
pambase upgrade carries its own correctness.

One line is appended by stage 40, next to the `ldconfig` / `systemd-hwdb` / `fc-cache` /
`create-cracklib-dict` finalizers that are already there for the same class of reason:

```
session  optional  pam_mkhomedir.so  umask=0077 skel=/etc/skel
```

A domain user has no home directory until they log in once. `sys-auth/oddjob` is not in the tree
and pambase has no flag for this, so the line is ours; `pam_mkhomedir.so` ships with
`sys-libs/pam` and is already present in every image built to date.

## 3. What a join writes

Every path here is **new** — none of it exists in the shipped image, so none of it copies up a
vendor file, and `<id>-domain leave` removes exactly this list.

```
/etc/sssd/sssd.conf                                    0600 root:root
/etc/krb5.conf.d/<realm>.conf
/etc/krb5.keytab                                       0600 root:root
/etc/systemd/system/multi-user.target.wants/sssd.service
/var/lib/<id>/domain.json                              the state stamp
  optional:
/etc/sudoers.d/20-domain-admins                        --admin-group
/etc/polkit-1/rules.d/50-domain-admins.rules           --admin-group
/etc/systemd/timesyncd.conf.d/10-domain.conf           NTP=<dc>
```

All of it lands in the `/etc` overlay upper on `/var`, so it survives A/B updates untouched — the
same mechanism that already carries the installer's `passwd`/`shadow` shadowing and the autologin
drop-in (plan/01, plan/16 §5.4).

### 3.1 The generated sssd.conf

```ini
[sssd]
domains  = corp.example.com
services = nss, pam

[domain/corp.example.com]
id_provider     = ad
auth_provider   = ad
access_provider = permit
ldap_id_mapping = true
cache_credentials = true
krb5_store_password_if_offline = true
krb5_ccname_template = KEYRING:persistent:%U
use_fully_qualified_names = false
fallback_homedir = /home/%u
default_shell   = /bin/bash
ad_hostname     = <host>.<domain>
dyndns_update   = true
```

Four of those are decisions rather than defaults:

- **`access_provider = permit`** is what makes "any valid user in the domain can log in" true. The
  `ad` provider's default is `access_provider = ad`, which enforces the GPO *Allow log on locally*
  right and in practice locks everyone out of a freshly joined Linux box. Evaluating GPOs also
  needs `sssd[samba]`, which §6 declines. `--allow-groups` switches to `simple` for sites that
  want the opposite.
- **`ldap_id_mapping = true`** derives POSIX uids from the object SID algorithmically. The
  alternative wants `uidNumber`/`gidNumber` attributes in AD, which most domains do not populate.
- **`use_fully_qualified_names = false`** so people type `alice`, not `alice@corp.example.com`.
  Safe with a single domain; a site with forest trusts should flip it.
- **`fallback_homedir = /home/%u`**, not `/var/home/%u`. `/home` is a symlink to `/var/home`
  (plan/01), so both resolve; `/home/alice` is what `getent passwd` should show a human.

`enumerate` is left at its default of `false` and should stay there — enumerating a large domain
is slow and hammers the DC. §4.2 is the consequence.

### 3.2 sssd validates this file, and exits rather than warns

**Found 2026-09-07, by booting a guest against a live domain controller.** The first version of
this generator emitted two options sssd does not accept:

| emitted | what is wrong |
|---|---|
| `config_file_version = 2` | required by sssd **1.x**, removed in 2.x, and 2.13's validator rejects it. It is not in `sssd.api.conf` at all |
| `krb5_store_password_if_available` | **invented.** The real option is `krb5_store_password_if_offline` |

Neither is a typo anyone would spot by reading, and both look plausible. What made them expensive
is the failure mode: `sss_ini_call_validators` refuses an unknown attribute and **the daemon
exits**, so `<id>-domain join` reported a failed join, `adcli` having already succeeded and
created the computer account. The cause was three layers down in `systemctl status sssd`, on a
guest that powers itself off.

The fix is a stage-40 finalizer in the same family as the cracklib dictionary: render a
representative config with `<id>-domain join --print-config sssd` and run **`sssctl config-check`
inside the target chroot**, with the same sssd that will read it, and fail the build unless it
reports `Issues identified by validators: 0`. Cheap, and it catches this whole class before any
image is written. `tests/test-domain.sh` additionally pins the two specific names so they cannot
return silently.

## 4. `<id>-domain`

One implementation, two callers: the CLI a user runs on an installed machine, and the installer
(§5.2) through a shim. Shipped as `config/rootfs/usr/bin/distro-domain.in`, rendered to
`/usr/bin/<id>-domain` by the same `render_dest_name()` rebranding that produces `<id>-update`.

```
<id>-domain join --domain D --user U [--password-stdin] [--root PATH]
                 [--computer-name N] [--ou OU] [--admin-group G] [--allow-groups a,b]
<id>-domain status | leave | test | --print-config
```

`join`, idempotent, everything relative to `--root` (default `/`):

1. **Preflight.** Root privileges; `REALM` is the uppercased domain; SRV discovery via
   `adcli info`; a clock-skew check, because Kerberos rejects a skew over 5 minutes and the
   resulting error names neither the clock nor the cause; and computer-name validation — AD caps
   a computer's `sAMAccountName` at **15 characters**, and failing on that here is far kinder than
   letting `adcli` fail on it later.
2. `adcli join --domain=D --domain-realm=REALM --login-user=U --stdin-password
   --host-fqdn=<host>.<D> [--computer-name=N] [--domain-ou=OU] -K <root>/etc/krb5.keytab`
3. Write `sssd.conf` (0600 — sssd refuses to start on anything looser) and the krb5 include.
4. `chroot <root> systemctl enable sssd.service`; with `--root /`, `systemctl enable --now`.
5. Optional sudoers/polkit drop-ins; optional `NTP=` pointing at the DC.
6. Write `domain.json`.

`leave` reverses that list and runs `sss_cache -E`. It is a **local** unjoin and says so: the
computer account stays in Active Directory, because deleting it is a domain administrator's
privilege and quietly attempting it with credentials the user may not have is worse than not
trying. `status` reads the stamp and `sssctl domain-status`. `test` is the diagnostic path — SRV records, `kinit`, socket reachable —
because "domain login does not work" has a dozen causes and eleven of them are the network.

`--print-config` emits the generated files to stdout and touches nothing, which is what lets the
offline test suite diff them against golden files with no domain controller anywhere.

### 4.1 Time

`systemd-timesyncd.service` is already enabled in the vendor preset, so the common case needs
nothing. In an AD network the domain controller is the canonical time source, so `join` writes a
`timesyncd.conf.d` drop-in naming it. This is cheap insurance against the single most confusing
Kerberos failure mode.

### 4.2 The greeter must accept a typed username — and it already does

sssd does not enumerate (§3.1), so **no domain account will ever appear in a user list, in any
greeter, by design**. Manual username entry is therefore not a nicety: without it the desktop half
of this feature does not work at all, however well the join goes.

**RESOLVED 2026-09-02 against plasma-login-manager 6.6.6's source, and it needs no configuration.**
The greeter's `Main.qml:208-213` carries an unconditional action button:

```qml
BreezeComponents.ActionButton {
    icon.name: "system-user-prompt"
    text: i18ndc("plasma_login", "For switching to a username and password prompt", "Other…")
    onClicked: PlasmaLogin.GreeterState.loginState = PlasmaLogin.GreeterState.LoginState.UserPrompt
    visible: !userListComponent.showUsernamePrompt
}
```

**Other…** switches the greeter to a Username + Password prompt, and **List Users** (`:347`)
switches back. Its `visible` condition is precisely "the user list is currently being shown",
which is the only case where it is needed. A domain user types their name there. This is the same
shape as `kwallet-pam` in plan/03: the thing that looked like it needed configuration turns out to
need none.

Two things found on the way that are worth keeping, because both would have been guessed wrong:

- **Do not look at `/usr/share/sddm/themes/breeze`.** Those files ship with
  `kde-plasma/plasma-desktop` and belong to SDDM, which this image does not use. PLM's greeter is
  `/usr/lib64/libexec/plasma-login-greeter` with its QML compiled in, and its `Login.qml` is a
  *different* file with the same name. The SDDM theme has no "Other…" button, so reading it
  concludes, wrongly, that the feature is impossible.
- **The user list is not configurable, and the obvious lever is a trap.**
  `GreeterState.qml:37` is `beyondUserLimit: UserModel.rowCount() === 0 || rowCount() > 7` — a
  hardcoded 7, with no config key. The model is bounded by
  `PlasmaLoginSettings::minimumUid()/maximumUid()` (`usermodel.cpp:104`), and those do **not**
  come from `plasmalogin.conf`: `getUids()` parses `UID_MIN`/`UID_MAX` out of **`/etc/login.defs`**.
  Narrowing that window to force the prompt would mean editing a `sys-apps/shadow` vendor file —
  copying it up into the overlay and freezing it forever, against this document's own §2 rule —
  and would break `useradd` on the way. The button makes all of that unnecessary.

Nothing is asserted in the build for this, because there is no artifact of ours to assert. It is a
fact about one upstream version, recorded here with the file and line so a PLM bump can be
re-checked against it, and T-DOM-3's graphical-login step is what would notice if it regressed.

## 5. The hazards

### 5.1 sssd must not run unjoined

`systemd-boot-check-no-failures.service` is enabled in the vendor preset and gates
`boot-complete.target` (plan/01, "Automatic Boot Assessment"). So on an unjoined machine, an
`sssd.service` that starts and fails is not a cosmetic wart — it fails the boot, burns a try, and
after three of them systemd-boot rolls the machine back to the previous image. On a *factory*
image, where there is no previous image, it simply fails every boot.

Defended twice, because one of these is a preset and presets have quietly not taken before:

- `disable sssd.service` (and the KCM/autofs socket units) in
  `usr/lib/systemd/system-preset/50-distro.preset.in`, applied by the explicit second pass stage 40
  already runs for `disable` lines — `--preset-mode=enable-only` ignores them.
- A shipped drop-in, `usr/lib/systemd/system/sssd.service.d/10-conditional.conf`, carrying
  `ConditionPathExists=/etc/sssd/sssd.conf`. A unit whose condition fails is recorded as
  **skipped**, not failed, which is exactly the distinction `boot-check-no-failures` cares about.

Stage 40 asserts no `sssd*` enablement symlink exists in the built image. T-DOM-4 asserts
`failed_units=0` on a booted, unjoined image.

### 5.2 File capabilities must survive two hostile steps

sssd's ebuild sets `FILECAPS` on `usr/libexec/sssd/{ldap_child,krb5_child,sssd_pam}` —
`cap_dac_read_search` so those helpers can read the keytab, plus `cap_setuid,cap_setgid` on
`krb5_child`. Lose them and authentication fails with a permission error nowhere near the cause.

Two steps in this pipeline are known to eat exactly this kind of metadata, and both have already
produced a bug of this shape:

- **`ROOT=$TARGET` merges skip work that assumes the live root.** `sys-libs/cracklib`'s
  `pkg_postinst` is guarded on `[[ -z ${ROOT} ]]` and had therefore never run in this project's
  history, which is why Calamares rejected every password (plan/16). Whether `fcaps.eclass`
  applies caps under a non-empty `ROOT` must be **checked with `getcap`**, not assumed.
- **`mkfs.erofs` flattened ownership** under `--all-root`, which broke dbus activation, every
  polkit rule and `unix_chkpwd` at once (plan/16). The fix added an assertion that reads the built
  EROFS rather than the tree it came from. Capabilities get the same treatment, and the same
  non-vacuity guard: finding no sssd helpers means the check proved nothing, not that there was
  nothing to protect.

**How the image half is actually read, because the obvious way is wrong.** Measured with
erofs-utils 1.8.10 on a two-file probe, before the assertion was written:

| | `getcap` after `fsck.erofs --extract --xattrs --preserve` | `dump.erofs --path=` |
|---|---|---|
| file **with** `cap_dac_read_search` | **nothing** | `Xattr size: 48` |
| file without | nothing | `Xattr size: 0` |
| with `mkfs.erofs -x-1` (xattrs off) | nothing | `Xattr size: 0` |

`fsck.erofs --extract` restores `user.*` xattrs and **silently declines `security.*`**, so the
extract-and-getcap approach reports "capability lost" on an image that has one — a false failure
on every build. `dump.erofs` cannot print xattr *values*, but its `Xattr size` discriminates
perfectly, including against `-x-1` as a real negative control. Since portage sets no `user.*`
xattrs on these binaries, a staging copy whose only xattr is the capability (proved by `getcap`
in half 1) plus a non-zero `Xattr size` in the image is that capability and nothing else. That
pair is the assertion, and extracting 2.7 GiB on every build to check three files is avoided as
a bonus.

### 5.3 CONFIG_PROTECT, and a defect this feature only happened to expose

**Found 2026-09-02, on the first build.** `sys-auth/pambase` merged with `USE=sssd`. Its VDB
recorded `USE=sssd`. `pam_sss.so` was installed. Every package audit passed. And
`/etc/pam.d/system-auth` was still the `pam_sss`-less version from a build nine days earlier —
with the correct twelve-line stack sitting beside it, unused, as `._cfg0000_system-auth`.

Portage does not overwrite a file under `CONFIG_PROTECT`. It writes the new version alongside and
leaves it for `etc-update` — a human, on a running machine, deciding whether to keep local edits.
**There is no human here and there are no local edits**: every merge in this pipeline goes into a
freshly emerged root under `ROOT=$TARGET`, so the "old" file is only ever a previous build's
vendor copy. Left alone, the update is silently discarded and the image ships whatever the first
build that ever created that file happened to write.

Three files were pending in the desktop target: `nsswitch.conf`, `pam.d/system-auth` and
`pam.d/system-services`.

This is the third bug of exactly this shape this project has hit, and the family is now worth
naming: **a build-time detail with no trace anywhere near the symptom.**

| | what was true | what it looked like |
|---|---|---|
| `sys-libs/cracklib` (plan/16) | `pkg_postinst` is `[[ -z ${ROOT} ]]`-guarded, so the dictionary was never built | Calamares rejected every password |
| `mkfs.erofs --all-root` (plan/16) | ownership flattened, so dbus could not exec its setuid helper | the installer's disk picker was empty |
| `CONFIG_PROTECT` (here) | the config update was written and then ignored | domain authentication would simply fail |

In all three the package is installed, correct, and present in the audit list. The fix is the same
shape as cracklib's: a step in stage 40 that does what the merge could not, plus an assertion that
it happened. Stage 40 applies every `._cfg????_*` **before** `install_rootfs_overlay` — vendor's
new file replaces vendor's old one, then this repo's own config replaces both, and reversing that
order would let a package update clobber what `config/rootfs` ships — and the verify block fails
the build if any survive.

**It is not specific to Active Directory.** Any pambase, glibc or shadow update that touched a
protected file has been silently discarded for as long as this pipeline has existed. This feature
is only what made it visible, because it is the first one whose entire behaviour lives in a
`CONFIG_PROTECT`ed file.

*What the generated stack turned out to be, and why it is safe unjoined:*

```
auth      [default=1 ignore=ignore success=ok]  pam_usertype.so isregular
auth      [default=3 ignore=ignore success=ok]  pam_localuser.so
auth      sufficient  pam_unix.so nullok
auth      sufficient  pam_sss.so forward_pass
account   [default=bad success=ok user_unknown=ignore]  pam_sss.so
session   optional    pam_sss.so
```

`pam_localuser` and `pam_usertype` short-circuit local accounts before `pam_sss` is reached at
all, `pam_unix` is `sufficient` and comes first, and the account line ignores `user_unknown`. So
an unjoined machine never consults sssd on the login path — which is the property §2 promises and
T-DOM-4 checks.

### 5.4 The AD provider is a USE flag, and every other assertion passes without it

This section exists because §1's decision table and the `package.use` comment that implemented it
both said the same wrong thing: that `sys-auth/sssd[samba]` "gates only the PAC responder and GPO
support" and that "the `ad` provider itself is unconditional". A domain join proved otherwise.
Upstream's `Makefile.am`, at the pinned `sssd-2.13.1`:

```make
sssdlib_LTLIBRARIES = \
    libsss_ldap.la \
    libsss_krb5.la \
    libsss_proxy.la \
    libsss_simple.la \
    $(NULL)

if BUILD_SAMBA
sssdlib_LTLIBRARIES += \
    libsss_ipa.la \
    libsss_ad.la
endif
```

The AD provider is built inside that conditional and nowhere else. Gentoo's ebuild passes
`$(use_with samba)`, so `USE=-samba` produces an sssd with no `libsss_ad.so`.

**What made this expensive is everything that did not fail.** On the `-samba` image:

- stage 40's `sssctl config-check` reported *Issues identified by validators: 0* — the generated
  `sssd.conf` is syntactically perfect and `id_provider = ad` is a valid value;
- stage 40's PAM, NSS, krb5 and enablement-symlink assertions all passed;
- stage 50's survival assertions passed — `sssd`, `adcli`, `pam_sss.so`, `libnss_sss.so`,
  `nsupdate` and the CLI were all present and correct;
- stage 60's capability assertion passed on all three helpers;
- the offline suite passed, 93 assertions;
- T-DOM-4 passed: the unjoined image booted clean with `failed_units=0`;
- **and the join itself succeeded.** `adcli` authenticated to the DC, created the computer account
  `IMMOS-5DBE4` in the directory, and wrote `/etc/krb5.keytab`.

Only then, starting the daemon the join had just enabled:

```
[be[immos.test]] [dp_module_open_lib] (0x0010): Unable to load module [ad] with path
  [/usr/lib64/sssd/libsss_ad.so]: cannot open shared object file: No such file or directory
[be[immos.test]] [dp_load_targets] (0x0020): Unable to load target [id] [80]:
  Accessing a corrupted shared library.
```

Nothing short of a real join against a real directory could have caught it, which is the argument
for T-DOM-3 restated as evidence rather than as a plan.

**The general shape, which is not about sssd.** A daemon whose behaviour is `dlopen()`ed plugins
has two independent questions — *is the daemon installed* and *can it load what its config names*
— and every assertion in this repo was asking only the first. `sssctl config-check` is not the
second question either: it validates the file, and a provider name is just a string until the
back end tries to open it. Both stages now derive the provider from
`<id>-domain --print-config sssd` and check for `libsss_<provider>.so`, so changing `id_provider`
without shipping its module fails the build rather than the login.

**What the flag costs, measured.** Less than the old comment feared, and most of it was already
paid: `net-fs/samba` is in all three locks (§6.4), and `winbind` adds no package — it builds from
samba's own tree, and samba's `REQUIRED_USE` constrains only the other direction. `USE=samba` also
turns on `--enable-pac-responder` and builds `libsss_ipa.so`. Neither is wanted; both are small.
`access_provider = permit` (§3.1) still means no GPO is ever evaluated — the flag is here for the
provider module, not for what the old comment thought it bought.

**Confirmed by relock across all four locks, 2026-09-07.** "adds no package" is now a measurement
rather than a reading of the ebuild. Re-resolving every profile against the corrected USE gave
**zero atom movement in all of them** — `desktop` 674, `installer` 672, `console` 492, `builder`
492, each reported by `relock.sh` as *"no drift, all at their locked versions"*, with the atom
lists byte-identical to the previous locks. The only line that changed in any of the four files
is `PORTAGE_CONFIG_HASH`, and all four now carry the same one. That is the useful property: the
flag that carries the AD provider is invisible to the dependency graph and visible only in what
the packages *contain*, which is exactly why the build passed without it and why the assertions
in §5.4 had to check for the module file rather than the package.

**And it brought a second domain client into the image.** `winbind.service` is a real unit that a
`systemctl preset-all` would enable, and started unjoined with no usable `smb.conf` it fails —
which on this distro is §5.1's failed boot and a rollback. Worse, the two enablement-symlink
assertions in stages 40 and 50 globbed `sssd*`, so the unit that would have done it was the one
name they did not look for. The preset disables `winbind.service`, `winbindd.service` and the two
`sssd-pac` units by name, and both globs are now `sssd*` or `winbind*`.

## 6. What this costs

### 6.1 Already present, so free on desktop and installer

`net-fs/samba`, `app-crypt/mit-krb5`, `net-fs/cifs-utils`, `sys-libs/{talloc,tdb,tevent}`,
`sys-apps/keyutils`, `net-dns/c-ares`, `dev-libs/{popt,jansson,libunistring,libnl,libpcre2}`.
The AD stack lands on top of a surprising amount of its own dependency closure, because

### 6.4 samba on the console profile — an accepted regression

`console` today has none of §6.1. sssd needs `virtual/ldb`, and the resolution is forced:

```
virtual/ldb-2.11.0  ->  net-fs/samba:0/2.11.0     (stable)
virtual/ldb-2.9.2   ->  sys-libs/ldb:0/2.9.2
net-fs/samba        ->  RDEPEND contains  !sys-libs/ldb
```

The two providers block each other, and the stable virtual is the samba one. Desktop and installer
already have samba, so they must resolve that way; forcing console onto `sys-libs/ldb` would give
it a different ldb ABI and fork `sys-auth/sssd` into two binpkgs — breaking the one rule that
makes multiple profiles cheap (plan/16 §3.2: *"a profile selects package sets; it must not change
USE flags"*, whose whole purpose is that shared packages resolve to one binpkg).

So **console accepts `net-fs/samba` and the perl interpreter it brings**, and every profile
resolves `virtual/ldb` identically.

**Measured 2026-09-02: 428 → 492 atoms, +64.** Three quarters of that is one dependency edge.

Sixty-four atoms on a 428-atom profile is a real regression and it belongs in the open. If it is
judged disproportionate, the decision it reopens is plan/16 §10 question 6 — whether `console`
should remain a profile at all, now that M1 is long past — not this one.

**Built and confirmed 2026-09-06: 428 → 492 in the lock, 0 removed, 0 version changes, and

### 6.6 One mode at a time (added by plan/19)

`<id>-domain join` now refuses on a machine enrolled in managed mode ([plan/19](19-managed-mode.md)
§8.7), naming `<id>-managed leave` as the way out; `<id>-managed enroll` carries the mirror of the
check against `/etc/sssd/sssd.conf`. Both refusals are **preflight** — before `adcli` runs and
before a single file is written — which is what makes "refuses and writes nothing" true rather
than merely likely, and T-MAN-7 asserts the ordering rather than just the refusal.

There is no technical reason the two would collide: sssd's uids are SID-derived and far above
60000, and managed uids are capped at 60000 by `/etc/login.defs`. The exclusivity is a support
decision — two systems provisioning accounts on one machine is a burden with no user behind it.

## 7. The installer

> **Superseded in part by [plan/21](21-installer-accounts-page.md).** Everything below described
> the feature as a checkbox on Calamares' *stock* users page, which is how it shipped. plan/21
> replaced that page: domain join is now the third **mode** of our own `accounts` page, the
> `/usr/bin/realm` shim is deleted, and §7.2's conclusion is reversed — see the notes in each
> subsection. §7.3 and §7.4's *reasoning* survives intact and is the reason the new job looks
> the way it does; only the code that carries it moved.

### 7.1 Calamares already has an Active Directory page

`config/calamares/modules/users.conf.in` has carried `allowActiveDirectory: false` since Phase A,
copied from upstream's example. Setting it `true` reveals, on the existing users page, a
**Use Active Directory** checkbox with Domain, Domain Administrator, password and IP fields
(`UsersPage.cpp:301-313`). No new module, no new page, and the ~80 translations come with it.

`Config.cpp:1088` then appends an `ActiveDirectoryJob` **before** `SetupGroupsJob` and
`CreateUserJob`. That job does exactly two things (`ActiveDirectoryJob.cpp`):

- if the IP field is non-empty, appends `<ip> <domain>` to `<rootMountPoint>/etc/hosts`;
- runs, **on the host and not in the chroot**, with the admin password on stdin and a **30-second
  timeout**:

```
realm join <domain> -U <adminLogin> --install=<rootMountPoint>/ --verbose
```

**That argv is the entire integration contract**, and it is the whole reason this is affordable.
`realm` is realmd, which is not in the tree — so the installer profile, and only the installer
profile, ships a ~40-line `/usr/bin/realm` shim that parses those tokens and forwards to
`<id>-domain join --root <path> --password-stdin`. It lives in `config/calamares/system/`, which
is already the installer-only install path, and stage 40 asserts it is present on `installer` and
absent everywhere else — the same converse assertion pattern that guards `/etc/calamares` itself.

> **plan/21:** deleted. With the stock users module out of the sequence, nothing calls `realm`
> any more, and `accountsetup` runs `<id>-domain join` directly. The assertion is now the
> inverse — stage 40 dies if `/usr/bin/realm` exists on the medium, because a file with that
> name that is not realmd is worse than no file at all. The shim's argv parsing goes; its
> exit-code mapping and its `domain-pending.json` writer move into the job verbatim.

### 7.2 Why not a custom page

> **Reversed by [plan/21](21-installer-accounts-page.md).** The Descriptor.h finding below is
> still exactly true and is *why* the new page is a compiled plugin. What changed is the
> cost/benefit: plan/19 Phase D built the machinery this section called "real new machinery"
> — an in-repo ebuild repository that lets Portage compile a Calamares plugin against the
> target's own Qt6/KF6 — for the managed-enrolment page, so the second plugin was nearly free.
> And the last paragraph's conclusion turned out to be a description of a *default*, not of a
> requirement: the local account is still not redundant in domain mode and is still created
> there, exactly as argued below. It is redundant in **managed** mode, which this section did
> not know about yet, and that is the case a strict either/or was needed for.

Checked against the Calamares 3.4.2 source rather than remembered:

```c++
// src/libcalamares/modulesystem/Descriptor.h
enum class Interface { QtPlugin,  // Jobs or Views
                       Python,    // Jobs only
                       Process }; // Deprecated interface
```

`ModuleFactory.cpp:53` accepts only `Interface::QtPlugin` for `Type::View`. **There is no QML or
Python view interface.** `welcomeq`, `usersq` and `notesqml` are compiled C++ plugins that render
QML internally, and their QML binds to properties defined by the C++ `Config` — so re-skinning one
cannot add an OU field or change which jobs get created. PythonQt view modules existed in 3.2 and
were removed before 3.3.

A custom page is therefore C++: a Qt6/KF6 plugin compiled against the target's Calamares headers,
which cannot be built in the builder root because its Qt6 comes from the binhost and need not
ABI-match the target's. That is real new machinery, and it buys a strict either/or that this OS
does not actually want: **the local account is not redundant here.** It owns wheel, sudo and polkit
admin, it receives the subuid range rootless podman needs (plan/13), and on a root filesystem with
no rescue shell and no package manager it is the only way back in when the DC is unreachable. The
stock page's additive shape — a local administrator, optionally also joined to a domain — is the
shape this system should have.

Consequences accepted with it: no OU field, so computer accounts land in `CN=Computers`; no
admin-group field; the 30-second cap; and — the one that turned out to matter — no way to
validate the domain before the destructive steps have run, because the page never publishes what
the operator typed anywhere an earlier module could read it. §7.4 is what that costs and how it
is contained. All are reachable later from Phase E if they bite.

> **plan/21:** all four are gone. The Advanced section carries `--ou`, `--admin-group` and
> `--computer-name`; the cap is the job's own; and the page publishes everything it collects to
> GlobalStorage (passwords excepted, which go to a 0600 file on tmpfs), so a `Check domain`
> button can run `<id>-domain verify` before Next. It is advisory and does not block — a failed
> join still cannot brick this mode, for §7.2's own reason.

### 7.3 The hostname ordering trap

`ActiveDirectoryJob` is appended at `Config.cpp:1088`; `SetHostNameJob` at `:1109`. **The join
runs before the hostname is written.** At that moment the target's `/etc/hostname` is still the
image's, and the live medium's own hostname is `<id>-<machineid5>` — so the computer account would
be created under a meaningless name, silently, and the machine would answer to a different one
forever after.

`Config::setHostName` inserts the user's choice into GlobalStorage as they type it
(`Config.cpp:278`), and `imagedeploy` runs in the exec phase, after every page. So `imagedeploy`
writes `<root>/etc/hostname` from GlobalStorage immediately after it mounts the /etc overlay, and
the shim reads it back. `SetHostNameJob` later writes the same value, which makes this a
harmless duplicate rather than a conflict — and it keeps the local module count at three, which
`tests/test-installer.sh` hard-asserts.

> **plan/21:** the trap is gone rather than avoided, because the ordering is now ours: the
> `accountsetup` job writes `/etc/hostname` and *then* joins, in one function, in that order.
> `imagedeploy` still writes it early and that write is still load-bearing — it is what makes
> the hostname independent of which module ran first — so both remain.

### 7.4 The installer verifies; it does not enroll itself — and a failed join must not fail the install

Two separate things, and it is worth separating them because the first is the question people
ask and the second is the one that bites.

**The live medium never joins anything.** Every path in `<id>-domain` is relative to `--root`,
and the shim always passes `--install=` through as that root: `adcli` is told
`--host-keytab=<root>/etc/krb5.keytab`, `--host-fqdn` is built from `<root>/etc/hostname` (§7.3),
sssd is enabled with `systemctl --root=<root>`, and the clock-skew note is explicitly guarded to
the `--root /` case. No computer account is ever created for the medium, no keytab is written to
it, no sssd runs on it. The one credential that *does* touch the medium is the domain
administrator's TGT during verification, and that is deliberately confined to a throwaway
`FILE:` ccache and destroyed — the default `KEYRING:` cache would leave a domain admin's ticket
sitting in the live session's keyring.

The enrollment itself has to happen during the install, and cannot be deferred: the keytab is the
machine's own credential, only the DC can issue it, and it takes domain credentials that exist
only while the operator is standing at the installer. Deferring means the installed machine boots
unjoined and someone with domain rights has to come back to it.

**Verification cannot be moved before the disk is written.**
> **plan/21:** it can now, and it is — as an advisory `Check domain` button, because the page
> is ours and publishes what it collects. It still does not *block*, for the reason the rest of
> this section gives. The one place where blocking became correct is managed mode, which
> creates no local account and therefore has no fallback: plan/21 §3.

`Config` keeps the domain, the admin
account and the password in plain members and hands them straight to the job — nothing writes them
to GlobalStorage. So no module that runs earlier can see them: not a `shellprocess` step ahead of
`partition`, not `contextualprocess`, not a fourth local module. `/usr/bin/realm` is the first
code in the entire installation that learns a domain was asked for, and by then `partition` and
`imagedeploy` have run. Closing that gap needs the C++ view module §7.2 declined.

**Which makes the shim's exit code the whole safety mechanism.** `ActiveDirectoryJob::exec()`
returns `JobResult::error` on a non-zero exit, and Calamares stops on the first job that errors.
This job is appended at `Config.cpp:1088`, *before* `SetupGroupsJob`, `CreateUserJob`,
`SetPasswordJob` and `SetHostNameJob` at `:1097-1109` — its own module's remaining jobs — and long
before `removeuser` and `imageidentity` in `settings.conf`'s exec list. So a domain controller
that is merely unreachable, which is a Tuesday, would stop the install on a disk carrying the
entire OS and a working bootloader, with:

- **no account the operator chose**, because `CreateUserJob` never ran;
- **`<live_user>` still in `/etc/passwd`**, because `removeuser` never ran; and
- **that account still autologging in**, because `imageidentity` never ran.

`removeuser.conf.in`'s header already reasons about the neighbouring hazard — "a machine with
neither account and no root password is unreachable" — but it reasons about `removeuser` running
*before* `users`, not about `users` aborting halfway through itself. An installed machine that
boots straight into the live medium's throwaway session, and is presented to the operator as a
*failed* installation they are unlikely to go looking inside, is worse in every direction,
security included, than an installed machine that is simply not joined yet and says so.

So the shim:

1. **verifies first** — `<id>-domain verify` bounds each check with `timeout`, because the job is
   killed at 30 seconds and the join needs most of it;
2. **writes nothing** if verification fails — `join` preflights through the same code and returns
   before it creates a single file, which is what makes step 3 honest;
3. **records the attempt** in `<root>/var/lib/<id>/domain-pending.json`, which `<id>-domain
   status` reports first, so the machine says out loud that a join was wanted and did not happen;
4. **exits 0 regardless**, so `CreateUserJob`, `removeuser` and `imageidentity` all still run.

Joining afterwards is one command. Recovering from the other outcome is a reinstall.

**`verify`'s exit codes are an interface**, not diagnostics — the shim branches on them to choose
what to tell the operator, and `join` passes them straight through:

| | |
|---|---|
| `0` | the domain answered and, if `--user` was given, the account authenticated |
| `2` | the domain could not be reached — `adcli info` covers DNS SRV discovery, routing and the DC being alive in one command, and needs no credentials |
| `3` | the domain controller rejected the account |
| `4` | the clock is outside Kerberos' five-minute tolerance — split out because it is the failure Kerberos reports least legibly |

The credential half is what answers the question the installer is really being asked: reaching a
controller proves the network, but a Kerberos AS-REQ proves the realm, the account *and* the
clock, which together are what "domain logins will work on this machine later" actually rests on.
`kinit`'s presence is asserted in stage 50 — `verify` degrades to a reachability-only check
without it rather than failing, so its absence would cost nothing visible at build time and the
entire credential half at install time.

*And the two things this document listed as unverified are now answered:*

- **`fcaps.eclass` DOES apply under `ROOT=$TARGET`** (§5.2's first half). Measured with `getcap`
  on the built target: `ldap_child` and `sssd_pam` carry `cap_dac_read_search=p`, `krb5_child`
  carries `cap_dac_read_search,cap_setgid,cap_setuid=p`. The worry was reasonable — cracklib's
  `pkg_postinst` is the precedent — but it does not apply here, and the assertion stays because
  the answer could change with an eclass revision.
- **`sys-auth/pambase[sssd]` generates the right stack, and it was being thrown away** (§5.3).
  That is the finding of the whole phase, and it was never an Active Directory bug.

The relock recipe, per profile, `desktop` first because `installer` stages its artifacts:

```sh
RELOCK=1 bash scripts/build.sh --only 20 --profile "$P"
RELOCK=1 bash scripts/build.sh --only 30 --profile "$P"   # exits 1: the target no longer matches
bash scripts/relock.sh --all --profile "$P"               # review out/reports*/lock.diff
cp out/reports*/"$P".lock.generated config/portage/lock/"$P".lock
bash scripts/build.sh --from 20 --profile "$P"            # exits 1: the audit list drifted
cp out/reports*/packages.txt config/portage/expected-packages."$P".txt   # keep the header
bash scripts/build.sh --from 50 --profile "$P"
```

Both of those non-zero exits are the gates doing their job, not failures. `RELOCK=1` on stage 20
is required and not a shortcut: stage 20's one-way header assertion is what stops the build in the
first place, and re-resolving the lock needs stages 20 and 30 to have run. `build.sh` forwards it
for exactly this — it did not before, and the recipe in plan/15 died on its own first line.

`relock.sh --builder` is needed too, and its *content* is a **header rewrite only**: measured, the
builder's closure is unchanged at 492 atoms and only `PORTAGE_CONFIG_HASH` and `PROFILE_SETS`
move. Its *cost* is not free, though, and it is worth knowing before running it. The Dockerfile
`COPY`s `builder.lock`, so rewriting the file invalidates that layer and everything after it —
and a Docker layer resumes from the state before it ran, not from the finished builder root. So
the next build re-runs the builder's whole emerge (~176 packages, all from the binhost as
binaries, `dev-lang/rust-bin` among them) rather than skipping it as already-installed. Minutes,
not hours, and only once per relock — but it is the reason `builder/Dockerfile` uses a
single-file `COPY` rather than copying the lock directory, which would put this on every
`relock.sh --security` too.

**Phase B — the test domain controller. RUN, AND ITS EXIT CRITERION MET, 2026-09-07.** `tests/ad-dc/` (a
container image built *from* the pinned builder, emerging `net-fs/samba[addc]` and provisioning a
throwaway `IMMOS.TEST` domain), `scripts/lib/ad-dc.sh` for its lifecycle, and
`build.sh --with-test-dc` to stand it up around stage 70.

**The design changed on one point while it was being written, and it is the point the phase
existed to settle.** This section originally said `net-fs/samba[addc]` "in the *builder* image".
That is wrong, and `builder/Dockerfile`'s own long note says why: portage evaluates
`REQUIRED_USE` and slot operators for **target** packages against whatever `/` says about the
same package name, which is the entire reason that file mirrors `package.use/image` verbatim.
`addc`'s `REQUIRED_USE` is `json python !system-mitkrb5 winbind` — samba with its own bundled
Heimdal — and letting that near the resolution that produces the product image is exactly the
class of accident the mirror exists to prevent. So the DC is a separate image, and
`tests/test-domain.sh` asserts that the builder's samba line is still the target's, verbatim.

**The networking answer, which is smaller than expected.** Three hops:
`guest --(slirp)--> stage-70 container --(docker bridge)--> DC`. QEMU's user-mode networking NATs
outbound TCP and UDP, so LDAP, Kerberos and kpasswd need nothing at all. DNS looked like the hard
part, because AD is discovered through SRV records and QEMU answers the guest's DNS itself at
10.0.2.3 — but it answers by *relaying to the container's own resolvers*. So the whole mechanism
is one docker flag: `build.sh` runs stage 70 with `--dns <dc>`, and the guest's SRV lookups
arrive at the domain controller with **no guest-side configuration whatsoever**. The seeded
NetworkManager profile this section contemplated is not needed, which matters for more than
convenience: the guest under test is the shipped image, byte for byte, with one SMBIOS credential
and nothing else.

*Exit:* inside the guest, `getent hosts dc.immos.test` and `kinit testuser@IMMOS.TEST` both
succeed. DC-backed tests **skip, not fail**, when no DC is present — stage 80's live-profile skip
is the precedent, and `tests/test-domain.sh` asserts the skip path exists rather than trusting it.

**Met.** The domain provisioned (`IMMOS.TEST`, `testuser`, a `Linux Admins` group), and the guest
reported **`kinit=yes`** — a Kerberos TGT for a domain account, obtained inside QEMU against the
containerised DC. That single field proves the entire chain the design was unsure about: SRV
discovery, the slirp DNS relay, KDC reachability and the credential handoff.

*Three things had to be fixed to get there, and none of them was the part that looked risky:*

- **`ads? ( ldap )`, then `tdb[python]`/`tevent[python]`/`bind[gssapi]`.** samba's `addc`
  REQUIRED_USE chain is longer than §8 assumed, and the builder image mirrors only the flags the
  *target* needs, so the fixture had to state its own. All confined to `tests/ad-dc/`.
- **QEMU splits `-smbios type=11,value=…` on commas.** The domain credential is
  `domain=…,user=…,password=…`, so QEMU read `user=` as a second `-smbios` option and died with
  *"Invalid parameter 'user'"* before the guest booted. QEMU's escape for a literal comma is a
  doubled one; `run-vm.sh` now doubles them, and the guest still sees exactly what `--domain` was
  given. The other credentials never hit this because a URL and a mode name contain no commas.
- **The container's resolver is `127.0.0.11` on a user-defined docker network**, not the `--dns`
  address — on such a network docker's embedded resolver is mandatory and `--dns` only tells
  *it* where to forward. slirp relays the guest's DNS to whatever `/etc/resolv.conf` names, and a
  loopback nameserver is the one case libslirp handles inconsistently. Stage 70 now writes the
  DC's routable address into `/etc/resolv.conf` before booting, which removes the question
  entirely.

The design's own prediction — that `--dns` alone would be "the whole mechanism" — was therefore
half right: the relay works exactly as described, but only once the address it relays to is a real
one.

**Phase C — `<id>-domain`. WRITTEN 2026-09-02.** The CLI, its generated configuration
(golden-file tested through `--print-config`, which touches nothing), and the guest-side `domain`
test mode that drives join → resolve → kinit → PAM → home → leave and reports all of it on one
line. §4.2's greeter question was the one piece expected to need work and turned out to need
none — the "Other…" button is already there.
*Exit:* **T-DOM-3** — join a running desktop image to the Phase-B domain, resolve and authenticate
a domain user, get a home directory created, log in graphically; then leave, and local login still
works.

**Met 2026-09-07**, verbatim from the guest, against the live Samba DC:

```
join=ok  domain_user=yes  domain_uid=38801103  kinit=yes  pam=yes  login=yes  home=yes
sssd=active  failed_units=0  left=ok  sssd_after=inactive  local_user=yes  conf_gone=yes
```

Read left to right that is the whole feature: the machine joined; a domain account resolves
through NSS with a SID-derived uid nobody assigned; it holds a Kerberos ticket; it authenticates
through PAM; it completes a **real console login** on the `login` → `system-local-login` →
`system-login` stack; and `pam_mkhomedir` created its home on the way through. `failed_units=0`
throughout is §5.1 holding while sssd is legitimately running. Then `leave` reverses it: the unit
goes back to inactive, `sssd.conf` is gone, and the local account still logs in — the property
that matters most, because it is the way back in when the DC is unreachable.

It took four build cycles to get that line, and **the last three failures were all in the
harness** — the two `login`/`home` traps below, and a marker line long enough to be refolded by
the agetty sharing the console, which split `conf_gone=yes` onto a continuation the parser never
read and reported it as "sssd.conf survived the leave". The guest now emits one short
`IMAGE-FIELD: key=value` line per field *before* the summary, and the harness reads those in
preference; lines that short cannot fold. The prefix deliberately omits the summary marker so it
does not end the boot watcher's wait early.

That is the phase's real lesson, and it generalises past this feature: **a check that passes for
the wrong reason is worse than no check**, and its mirror — a check that *fails* for the wrong
reason will send you to rewrite working code. §5.4 is the first kind and cost a rebuild; the `su`
trap below is the second and nearly cost a correct PAM stack.

**Phase D — the installer path. WRITTEN 2026-09-02.** §7: `allowActiveDirectory: true`, the
`realm` shim, the `imagedeploy` hostname write, and the profile assertions both ways (the shim
must exist on `installer` and must not exist anywhere else).
*Exit:* **T-DOM-1**, **T-DOM-2** and **T-DOM-5**. All three drive a real install, so all three
depend on plan/16 §10 question 5 — Calamares' unattended path, still unestablished. Until it is,
they are documented manual guest runs; T-DOM-3 and T-DOM-4 are the automatic pair. T-DOM-5's
*shim* half is covered offline with stubs (`tests/test-domain.sh` §5b) and its Calamares half —
that a `JobResult::error` is never raised in the first place — is the part that needs the guest.

**Phase E — deferred, and each after a measurement.** Trimming `net-dns/bind` to `nsupdate`;
a C++ view module for a strict either/or with OU and admin-group fields; GPO access control via
`sssd[samba]`; `sudoers: sss` and the sudo responder.

**Three traps in T-DOM-3, each of which failed as something other than what it was.** All three
cost a full build cycle, and none of them was ever a defect in the feature.

**`su` has no controlling terminal under a systemd unit.** The reporter runs as a unit, and PAM's
conversation function opens `/dev/tty` to read a password: `su` fails with *"must be run from a
terminal"* **before it ever consults pam_sss**, which is indistinguishable on the wire from "the
domain user's password was rejected". It runs under `script -qec … /dev/null`, which allocates a
pty and passes stdin through. The report carries `pam=no-script` as a distinct value from `pam=no`
so the two can never be confused again.

**`su -` does not run `system-login`, and this document used to say it did.** A `-` gives a login
*shell*; it does not change the PAM *service*. util-linux registers `su -` as **`su-l`**, whose
stack includes `su`, which includes `system-auth` — and `pam_mkhomedir` is on `system-login`,
which is a different file that `su` never reaches. So the `su` check could prove authentication
and could **never** prove the home directory, and when `home=no` came back the placement of
pam_mkhomedir was not the thing that was wrong. The test was. T-DOM-3 now performs a **real
console login** under `login(1)`, which is the service that actually includes
`system-local-login` → `system-login` — the same stack `plasmalogin` substacks, so the graphical
path is covered by proxy. It writes `id -u` to a sentinel file and the harness compares that
against the uid sssd resolved, because a shell prompt appearing proves less than it looks like it
does.

**`login(1)` flushes typed-ahead input, twice.** It calls `tcsetattr(TCSAFLUSH)` at startup and
again before reading the password, and `TCSAFLUSH` discards everything already buffered on the
pty. Feeding the username immediately meant it was thrown away and the *password* landed in the
username prompt — reported, of course, as a failed login. Every fed line now waits for the prompt
it answers.

Offline suite, `tests/test-domain.sh`: `--print-config` output diffed against golden files;
nsswitch names `sss` and stage 40's module loop knows it; the preset disables `sssd*` and the
`ConditionPathExists` drop-in exists; `@domain` is named by every profile and its two atoms
appear in every `expected-packages.*.txt`.

> **Amended by [plan/21](21-installer-accounts-page.md).** Two of these cases described the shim
> and are gone with it: `users.conf.in` setting `allowActiveDirectory: true`, and the shim
> accepting **exactly** `join <domain> -U <user> --install=<path> --verbose` quoted from
> `ActiveDirectoryJob.cpp`. What replaced them asserts the same property one layer down and
> against a caller we own: `accountsetup` invokes `<id>-domain join --domain … --user … --root …
> --password-stdin`, with `--ou`/`--admin-group`/`--computer-name` appended only when non-empty,
> and the argv is asserted for **adjacency** so a flag cannot drift onto the wrong value. The
> Calamares-bump tripwire is not lost, it moved: stage 40 now dies if `/usr/bin/realm` exists at
> all, which is what a reappearing stock AD page would need.

Build-time: the stage 40, 50 and 60 assertions listed in §2, §5.1 and §5.2.

**And once, by hand, against a real Windows Server domain** — from both the CLI and the installer,
including a cached login with the network disconnected. Samba's AD DC is close to Windows but not
identical, and a real domain is the claim this feature actually makes.

## 10. Open questions

1. ~~**The greeter knob (§4.2).**~~ **ANSWERED 2026-09-02: none is needed.** PLM 6.6.6's greeter
   has an "Other…" button that switches to a username prompt (`Main.qml:208`). The question was
   asked because sssd never enumerates, so a domain account cannot appear in any user list; the
   answer is that the greeter already provides the other path. §4.2 records the two wrong turns
   available here — the SDDM Breeze theme, which is a different component with no such button,
   and `/etc/login.defs`, which is where the user-list bounds actually come from and is a vendor
   file this design must not edit.
2. ~~**QEMU DNS to the test DC (Phase B).**~~ **ANSWERED 2026-09-07: the slirp relay works, but
   only to a routable address.** QEMU answers the guest's DNS at 10.0.2.3 by relaying to the
   container's own `/etc/resolv.conf`, so SRV discovery needs **no guest-side configuration** —
   the guest under test stays the shipped image byte for byte. The catch was that on a
   user-defined docker network that file names `127.0.0.11`, docker's embedded resolver, which is
   the one case libslirp handles inconsistently; stage 70 writes the DC's routable address there
   before booting. Recorded in full in Phase B above.
3. ~~**`fcaps` under `ROOT=$TARGET` (§5.2).**~~ **ANSWERED 2026-09-02: yes, and EROFS keeps
   them.** `getcap` on the built target shows `cap_dac_read_search=p` on `ldap_child` and
   `sssd_pam` and `cap_dac_read_search,cap_setgid,cap_setuid=p` on `krb5_child`, and stage 60
   confirms all three survive into the assembled image. The assertions stay: the answer could
   change with an eclass revision, and the failure mode is an authentication error nowhere near
   its cause.
4. ~~**Measured cost (§6.2, §6.4).**~~ **ANSWERED, and it is in three places.** New atoms on
   `desktop`/`installer`: **+19** each (§6.2). The console delta: **428 → 492, +64**, three
   quarters of it behind one `dev-lang/perl` edge, with 421 → 479 in the post-prune audit list
   (§6.4) — a real regression, recorded rather than excused, and the thing that would reopen
   plan/16 §10 question 6 if it is judged disproportionate. The `sssd[samba]`/`samba[winbind]`
   correction on top of that: **zero atoms on every profile** (§5.4).
5. **Multi-domain and forest trusts.** Out of scope for v1; `use_fully_qualified_names = false`
   and a single `[domain/...]` section are the two things that would have to change.
